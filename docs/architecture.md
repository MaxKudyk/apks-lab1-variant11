# Архітектура AI-агента

## Загальна схема

Build Engineer — це спеціалізований GitHub Copilot-агент для автоматизації підготовки проєкту на Java 17, Maven, JUnit 5 і GitHub Actions. Він працює з поточним репозиторієм: спочатку аналізує його стан, потім виконує потрібні операції, перевіряє результат і звітує про зміни.

Агент має працювати лише в межах запиту користувача та зберігати вже наявні файли, налаштування й користувацькі зміни.

## Маніфест агента

Маніфест `.github/agents/build-engineer.agent.md` задає ім'я агента, його роль, опис призначення, інструменти та інструкції виконання. У ньому визначені відповідальність за структуру Java-проєкту, конфігурацію Maven і JUnit 5, а також CI для Windows, Linux і macOS.

Маніфест описує заплановані навички, команди й оркестратор `init`, а також правила зміни файлів, обмеження безпеки, повторюваність операцій і критерії успіху. Сам маніфест не реалізує команди або навички: вони мають бути створені окремо на наступному етапі.

## Заплановані навички

- **`project-scaffold`** — перевіряє наявну структуру та створює відсутні каталоги й файли Java-проєкту, не перезаписуючи користувацьку роботу.
- **`build-and-test`** — налаштовує Maven для Java 17 та JUnit 5, запускає збірку й тести та надає результати.
- **`github-actions`** — створює або обережно оновлює CI workflow GitHub Actions для Windows, Linux і macOS.

## Заплановані команди

1. **`git-init`** — перевіряє, чи репозиторій уже ініціалізовано Git, і виконує ініціалізацію лише за потреби.
2. **`create-project`** — готує структуру Java-проєкту, зберігаючи наявні файли.
3. **`create-build`** — налаштовує Maven для Java 17 і JUnit 5.
4. **`create-actions`** — готує GitHub Actions CI для трьох операційних систем: Windows, Linux і macOS.
5. **`check`** — перевіряє структуру проєкту, конфігурацію, збірку, тести та CI, повідомляючи про непідтверджені або невдалі перевірки.
6. **`init`** — оркестратор, який запускає п'ять попередніх команд у визначеному порядку.

## Послідовність і потік даних

`init` послідовно запускає `git-init` → `create-project` → `create-build` → `create-actions` → `check`. Наступний крок починається тільки після успішного завершення попереднього; перша помилка зупиняє весь процес.

Кожний етап отримує стан репозиторію та результати попередніх кроків, а також задані вимоги проєкту (Java 17, Maven, JUnit 5 і цільові платформи CI). Результатом є оновлений стан файлів і звіт про виконання:

| Етап | Вхідні дані | Результат, що передається далі |
| --- | --- | --- |
| `git-init` | Стан каталогу й Git-репозиторію | Підтверджений стан Git або повідомлення про помилку |
| `create-project` | Файли репозиторію та вимоги до Java-проєкту | Структура проєкту; список створених або вже наявних ресурсів |
| `create-build` | Структура проєкту та вимоги Java 17/Maven/JUnit 5 | Maven-конфігурація, необхідна для наступного CI-кроку |
| `create-actions` | Maven-команди збірки/тестування та вимоги до платформ | CI-конфігурація для Windows, Linux і macOS |
| `check` | Створені або наявні ресурси проєкту, Maven і CI | Результати перевірок та підсумковий статус |

Результати команд використовуються як контрольні умови оркестратора: успішний крок дозволяє перейти до наступного, а помилка містить назву етапу й причину та перериває `init`. Оркестратор не повинен повідомляти про повний успіх, якщо перевірки не пройшли або не були виконані.

## Помилки та перевірка

На кожному кроці агент має явно повідомляти про помилки, невдалі команди та перевірки, які неможливо виконати. Після налаштування збірки слід перевірити Maven build і тести JUnit 5; також потрібно перевірити, що CI охоплює Windows, Linux і macOS. Підсумковий статус має відрізняти успішні, невдалі та неперевірені результати.

Якщо для безпечного продовження потрібно перезаписати або видалити наявний вміст, агент має зупинитися, пояснити наслідки й отримати дозвіл користувача.

## Безпека та повторюваність

- Не видаляти наявні файли без явного дозволу користувача.
- Не перезаписувати наявні налаштування й не створювати дублікати конфігурацій.
- Не виконувати force-push і не змінювати захист гілок.
- Не виводити, не публікувати й не комітити секрети; для CI використовувати GitHub Actions secrets, якщо потрібні облікові дані.
- Перевіряти стан репозиторію перед створенням або редагуванням файлів.
- Повторний запуск має бути безпечним: повторно використовувати наявні ресурси та вносити лише потрібні зміни.

## Гілки `develop` і `feature`

У межах запропонованого процесу розробки гілка **`develop`** є спільною гілкою інтеграції перевірених змін. Для окремої функції або лабораторного етапу створюється **`feature/<короткий-опис>`** від `develop`. Робота виконується у feature-гілці, проходить перевірки та інтегрується в `develop` після перегляду змін.

Агент може допомагати працювати з файлами в поточній гілці, але не повинен самостійно змінювати правила захисту гілок або виконувати force-push. Згадані назви й потік описують рекомендовану організацію роботи, а не вже налаштовані GitHub-правила.
